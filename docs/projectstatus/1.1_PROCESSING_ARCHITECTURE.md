# Processing architecture

Tally Prime Connector has two complementary processing engines. C# is the primary engine; Python is the dedicated specialist engine. The C# desktop application always owns application lifecycle, Tally integration, SQLite, workflow orchestration, and Excel export.

```text
Standard processing

TallyPrime → C# Tally Integration → Normalized data → C# Core Processing → Reports / Excel

Specialist processing

TallyPrime → C# Tally Integration → Normalized data → C# Core Processing
                                                        ↓
                                           Python Specialist Processing
                                                        ↓
                                             C# result integration → Reports / Excel
```

## C# Core Processing Engine

`TallyPrimeConnector.Processing.Core` is the default engine for normalization-adjacent workflows, validation, filtering, grouping, aggregation, debit/credit calculations, reconciliation orchestration, duplicate detection, business rules, local jobs, reporting, and Excel preparation. It works without Python.

## Python Specialist Processing Engine

`TallyPrimeConnector.Processing.Specialist` defines `ISpecialistProcessingEngine` and `IPythonSpecialistRuntime`. It receives normalized `VoucherInfo` DTOs and structured options through `SpecialistProcessingRequest`, and returns `SpecialistProcessingResult`.

It has no Tally connection, database, desktop UI, or application-lifecycle access. The eventual installer will supply a private bundled runtime and dependencies; the application will not rely on global Python, PATH, pip, or virtual environments.

Phase 1.1 includes the C# boundary and the Python JSON-lines protocol skeleton. It intentionally does not implement packaged runtime execution, pandas pipelines, AI, ML, anomaly algorithms, or advanced statistics.

## Engine selection

`IProcessingEngineSelector` remains in the C# application layer. Standard job types use `CoreCSharp`. Job types beginning `specialist.` use `PythonSpecialist`. If the bundled runtime is unavailable, the specialist engine returns a structured unavailable result; it does not silently pretend the specialist job was processed by C#.
# Phase 01.1 — Processing architecture and developer tooling

Added the C# Core Processing Engine and Python Specialist Processing Engine architectural boundary. C# remains the primary engine and orchestrator. Python receives normalized data only through typed contracts and has no Tally, UI, or database access.

Added engine selection, bundled-runtime contracts, an unavailable-runtime implementation, a Python JSON-lines protocol skeleton, DI registrations, specialist test coverage, and processing architecture documentation. Runtime packaging and specialist algorithms remain deferred.

## Tally MCP and CLI foundation

Added foundation projects for a local Tally MCP adapter and a Tally Prime Connector command-line interface. The MCP adapter exposes safe tool-shaped operations through existing application contracts; it is not a Tally protocol implementation and does not bypass company security. A production MCP transport host must be selected and verified in a later phase.
