## Root cause and selected mechanism

The prior request asked the executable to export the **DayBook report** (`EXPORT / DATA / DayBook`). On this `1.1.7.1` installation, that report's HTTP export did not bind `SVFROMDATE`/`SVTODATE` to its report context: distinct requested ranges returned the same out-of-period vouchers. HTTP success and `STATUS=1` only confirmed export success, not report-variable binding.

`TSPLVoucherColl` is absent, so a built-in named collection cannot be relied on. The replacement uses the documented TDL extension point *inside a single export request* to define a `Voucher` collection. This definition is evaluated for that request only; it is not installed, saved, or persisted in Tally.

`TallyXmlRequestFactory.CreateVoucherCollectionRequest` emits the following structure (the exact production request includes the listed `FETCH` methods):

```xml
<ENVELOPE>
  <HEADER>
    <VERSION>1</VERSION>
    <TALLYREQUEST>EXPORT</TALLYREQUEST>
    <TYPE>COLLECTION</TYPE>
    <ID>TPC Read Only Voucher Scope</ID>
  </HEADER>
  <BODY><DESC>
    <STATICVARIABLES>
      <SVEXPORTFORMAT>$$SysName:XML</SVEXPORTFORMAT>
      <SVCURRENTCOMPANY TYPE="String">Aravali Dairy &amp; Agro Products Pvt. Ltd (FY2026-27)</SVCURRENTCOMPANY>
      <SVFROMDATE TYPE="Date">20260901</SVFROMDATE>
      <SVTODATE TYPE="Date">20260901</SVTODATE>
    </STATICVARIABLES>
    <TDL><TDLMESSAGE>
      <COLLECTION NAME="TPC Read Only Voucher Scope" ISMODIFY="No" ISFIXED="No" ISINITIALIZE="Yes" ISOPTION="No" ISINTERNAL="No">
        <TYPE>Voucher</TYPE>
        <FETCH>Date</FETCH><FETCH>GUID</FETCH><FETCH>MasterID</FETCH>
        <FETCH>VoucherTypeName</FETCH><FETCH>VoucherNumber</FETCH>
        <FETCH>Narration</FETCH><FETCH>PartyLedgerName</FETCH><FETCH>Reference</FETCH>
        <FETCH>LedgerEntries.*</FETCH><FETCH>AllLedgerEntries.*</FETCH>
      </COLLECTION>
    </TDLMESSAGE></TDL>
  </DESC></BODY>
</ENVELOPE>
```

The live response is `DATA / COLLECTION / VOUCHER`, with the directly exposed `DATE`, `GUID`, `MASTERID`, `VOUCHERTYPENAME`, `VOUCHERNUMBER`, narration/party/reference fields and ledger-entry lists required by the normalizer. Nested component `VOUCHER` nodes without a direct `DATE` are deliberately excluded.

## Company and date semantics

Company context is the exact currently loaded company name, `Aravali Dairy & Agro Products Pvt. Ltd (FY2026-27)`. Numeric code `100018` is never used as a guessed `SVCURRENTCOMPANY` value.

The verified date representation is an explicitly typed `YYYYMMDD` value, for example `20260901`. Boundaries are inclusive: the 1–10 September query returns both 1 September and 10 September vouchers, and none outside that interval.

## Ledger extraction

The selected mechanism does not claim a server-side ledger filter. It obtains the complete **verified date-scoped** voucher collection, then `ExtractionService` retains only vouchers containing a selected ledger entry. This is safe because `TallyXmlVoucherProvider` throws a `TallyProtocolException` before any downstream filtering if even one returned voucher falls outside the requested dates.

Live diagnostic: for `2026-09-02` and ledger `G Pay`, the complete scope had eight vouchers and the client-side membership filter selected exactly two: `AR/26-27/00385` and `AR/26-27/00386`. The diagnostic explicitly labels this as `CLIENT-SIDE AFTER VERIFIED DATE SCOPE`; it does not represent it as a Tally server-side filter.

## Implementation

- `TallyXmlVoucherProvider` now uses the ephemeral Voucher collection, not Day Book, and fails closed on out-of-range vouchers.
- `TallyProtocolDiagnostics` and the CLI `protocol-diagnostics` command report endpoint, mechanism, company, requested/actual dates, counts, voucher numbers/types, ledger names, totals, status, date scope, reconciliation, and optional client-side ledger result.
- The WPF composition root now uses the verified XML providers. Mock providers remain intact for tests/development.
- `TallyXmlResponseParser` normalizes all top-level `ALLLEDGERENTRIES.LIST` and `LEDGERENTRIES.LIST` records and item accounting allocations where present. It preserves the source signed amount in `VoucherEntryInfo.SourceAmount`, while the existing normalized `TransactionAmount` keeps an absolute `decimal` plus direction.
- Actual source convention is verified from the live outputs/fixture: `ISDEEMEDPOSITIVE=Yes` denotes Debit and `No` denotes Credit; `AMOUNT` remains signed. Reconciliation uses both facts, including negative round-off adjustments.
- XML 1.0-invalid control-character references such as `&#4;` are removed only at the XML parsing boundary; accounting text/amounts are not rewritten.

## Security

Only `EXPORT` requests are produced. The embedded TDL defines a collection only and contains no action, mutation, credential, company-protection, database/file, or memory operation. No `IMPORT`, `CREATE`, `ALTER`, `DELETE`, `CANCEL`, security bypass, direct Tally data access, Tally file modification, or Python-to-Tally communication was introduced.

## Remaining limitations

- Ledger selection is deliberately client-side after server-side date verification; a server-side ledger filter was not claimed or enabled.
- The collection fetches complete voucher ledger data within the requested date interval. Very large user-selected intervals should be requested in caller-controlled date batches; the provider never falls back to a full-financial-year Day Book download.
- Tally UI automation was not made a product dependency. The live HTTP collection evidence is the production verification source.
