## PARTIALLY VERIFIED

### Day Book date request

The request shape is the official Day Book `EXPORT / DATA / DayBook` shape with `SVFROMDATE` and `SVTODATE`. After the Day Book UI was confirmed working, the minimal official request was retried without an explicit company variable. Both `1-Apr-2025` and `1-Jun-2026` requests returned status `1`, five vouchers, all dated `2026-09-10`. This reproduces the issue independently of the company-name variable and proves that the result is not safely date-scoped for this request on this installation. The connector therefore does not claim production-safe date filtering.

The follow-up numeric-form request (`20250401`) returned Tally status `0` with no vouchers in the current session. This is not sufficient to establish a supported numeric date format because the active company/session changed and the response contained no useful error text.

### Company context `100018`

The user has confirmed that company code `100018` corresponds to the exact loaded company name `Aravali Dairy & Agro Products Pvt. Ltd (FY2026-27)`. An explicit `SVCURRENTCOMPANY=100018` request returned Tally status `0` and no groups, confirming that the code must not be sent in that variable. The connector must send the XML-escaped company name and may retain `100018` as application metadata once a contract field is added.

After the Tally process restarted, the active company response was `Aravali Dairy & Agro Products Pvt. Ltd (FY2026-27)`. With Tally restarted again and that exact XML-escaped name supplied, the Day Book request exceeded the 20-second HTTP timeout; a subsequent read-only company request also exceeded 15 seconds and the endpoint stopped responding to GET. A later retry passed the health check but the corrected-name Day Book request for `1-Jun-2026` again exceeded 12 seconds. Therefore the corrected-name date semantics remain unverified and a trustworthy UI reconciliation is still unavailable in this run.

### Ledger filtering

No supported live server-side ledger filter was proven. The existing safe design remains: verify date-scoped transaction data first, then filter ledger entries client-side only if the complete server-side date scope is demonstrated. No claim of server-side ledger filtering is made.

## BLOCKED

### Tally UI ground truth

The requested Day Book and Ledger Vouchers UI counts, dates, voucher numbers, and debit/credit totals were not captured by an automated UI session. Without the same loaded company, ledger, and period in the UI, reconciliation would be speculative.

### Date semantics

The live evidence is contradictory (human-form request returned out-of-period records; numeric-form request returned status 0 after session change). Exact date semantics remain blocked until TallyPrime is kept open with the intended company loaded and the same request forms are tested one at a time against UI export output.

### WPF live preview

The WPF application continues to default to mock providers. A live provider selector and live preview are not claimed complete because the date/ledger semantics are not trustworthy yet.
