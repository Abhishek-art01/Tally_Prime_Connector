# Phase 1.5 — Ledger-wise Transaction Extraction & Excel Export

Date: 2026-09-16

## Status

Complete. The Phase 1.4F verified `EXPORT / COLLECTION` mechanism remains the sole Tally transaction source. This phase adds bounded batch processing, exact client-side ledger membership, deterministic deduplication, ledger-wise reconciliation totals, and a ClosedXML workbook with one selected-ledger worksheet per sheet.

## Extraction architecture

```text
Company + dates + selected ledgers + batch size + .xlsx path
  -> bounded inclusive date batches
  -> verified TallyXmlVoucherProvider (read-only, fail-closed date scope)
  -> normalized VoucherInfo / VoucherEntryInfo
  -> GUID, MasterID, then cautious fallback deduplication
  -> exact canonical ledger-name membership
  -> ledger transaction results and reconciliation
  -> ClosedXML ledger-per-sheet workbook
```

`LedgerWiseExtractionRequest` uses `DateOnly`, `LedgerInfo`, a selected-group metadata value, `int BatchDays`, and a validated `.xlsx` output path. The default batch size is 31 days and is configurable in the WPF workflow and CLI. Batches are adjacent inclusive ranges: each ends at `from + BatchDays - 1` (or the requested end), and the next starts the following date. This prevents date gaps and overlaps.

The provider continues to request only each bounded interval using the Phase 1.4F ephemeral read-only Voucher collection. It still throws if any returned voucher falls outside that batch. Core repeats that check as a defense-in-depth data-scope guard; it never silently removes bad data and carries on.

## Ledger and group semantics

Ledger filtering remains explicitly **client-side after verified server-side date scope**. Names are compared as exact trimmed Unicode-normalized values; partial names do not match (`Bank` does not select `Bank Charges`). Selected ledgers with no matching entries remain in the result and receive an empty worksheet.

The selected group is workflow metadata. It can limit the ledger list used for selection, but the extraction does not claim a Tally server-side group transaction filter or apply any invented transaction group semantics.

## Identity, accounting, and reconciliation

Voucher deduplication keys are chosen in this order:

1. `GUID`
2. `MASTERID`
3. fallback: source id, date, voucher type, voucher number, party ledger, and reference

Duplicate identities must have equivalent voucher content; conflicting content stops extraction with a data-integrity error. Voucher numbers are never used alone.

The normalized source retains `GUID`, `MASTERID`, signed `SourceAmount`, absolute `decimal` amount, and debit/credit direction. The verified convention remains `ISDEEMEDPOSITIVE=Yes` for Debit and `No` for Credit. Worksheet Debit/Credit values use absolute amounts in their respective column; Source Amount remains the original signed value. Overall reconciliation uses Tally's signed source convention, including round-off entries, and reports `Balanced`, `Unbalanced`, or `NotApplicable`. Individual ledger totals are intentionally not required to balance.

## Excel output

`LedgerWorkbookExporter` produces one worksheet for every selected ledger, including zero-transaction ledgers. Each sheet contains:

```text
Date, Voucher Type, Voucher Number, Ledger, Party Ledger, Reference,
Narration, Debit, Credit, Amount, Source Amount, GUID, MasterID
```

Sheets have formatted headers, frozen top row, filters, accounting/date formats, deterministic ordering (date, voucher number/identity, source entry position), and fixed useful widths. Invalid Excel worksheet characters are replaced, names are limited to 31 characters, and collisions receive deterministic suffixes such as `Bank (2)`.

ClosedXML exposes no cancellable save operation. Cancellation is checked before workbook creation, before each worksheet/transaction row, and immediately before save; cancellation stops future batches and does not return a successful export result.

## WPF and CLI

The WPF composition root registers the Core ledger-wise extraction/export workflow and the ClosedXML exporter. The native Fluent-style connection workspace presents the gateway configuration, company/group/ledger cascade, exact ledger-selection grid, date and batch controls, workbook picker, progress/status, cancellation, preview rows, and workbook reveal action. It binds directly to the existing read-only workflow; visual gateway labels are configuration/status controls rather than a claim that a live query has already succeeded. Mock providers remain available for tests/development.

The composition-root CLI command is available for controlled local verification:

```text
ledger-export YYYY-MM-DD YYYY-MM-DD output.xlsx [--batch-days N] ledger [ledger ...]
```

It composes the verified Tally provider behind Core services and uses no additional protocol.

## Security and limitations

Only the previously verified read-only `EXPORT / COLLECTION` request is used. No `IMPORT`, create/alter/delete/cancel action, Tally configuration/file/database access, password/security bypass, memory operation, or Python interaction was added.

Ledger filtering is intentionally not claimed as server-side. Export data is accumulated per requested bounded batch; for a broad export the service retains only deduplication fingerprints, aggregate reconciliation values, and the selected-ledger transaction rows required by ClosedXML. It does not retain every non-selected voucher object or request an unbounded financial year in one call.
